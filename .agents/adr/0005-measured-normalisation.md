## Context

The normalisation rule exists **twice**: as SQL expressions in the index
columns and as the C# `Normalizer`. The specification (ADR-0005) says so and
demands a test:

> The rule therefore exists twice. A test must show over a large sample
> … that SQL and C# deliver the same search form.

The rule itself (ADR-0005) is written in three steps:

1. lower case,
2. German transliteration (`ä→ae`, `ö→oe`, `ü→ue`, `ß→ss`),
3. remove the remaining accents by **Unicode decomposition**.

The obvious C# implementation of step 3 is `char.ToLowerInvariant()` plus
`Normalize(FormD)` and dropping the combining marks. It does not work.

**Measured against SQLite 3.53.3** (`tools/FoldTableGenerator`, over the
whole Basic Multilingual Plane):

| | |
|---|---|
| Code points the tokenizer folds differently than `char.ToLowerInvariant` | **697** of 63 487 |
| …differently than "ToLowerInvariant + strip the precomposed diacritic" | **681** |

The differences are not academic:

| Input | The tokenizer | The obvious C# rule |
|---|---|---|
| `ĳ`, `ǳ`, `ﬀ` | unchanged — the digraphs and ligatures are **not** decomposed | decomposed (`ĳ` → `i`) |
| `ί` | unchanged — the Greek tonos is **not** removed | removed |
| `İ` | `i` | unchanged (.NET leaves `İ` alone) |
| `ẞ` | `ß` | unchanged |
| `µ` | `μ` (the Greek mu) | unchanged |

And the *order* of the steps is load-bearing: the tokenizer removes the
umlaut, so `Ä` folded first becomes `a` — and the transliteration, which
has to run first, would have nothing left to do.

Two more things the measurement settled:

- **The tokenizer works per character.** It does not normalise the text
  first: `e` + combining acute becomes `ecole` because the mark is
  dropped, not because the text was composed to `é`.
- **The tokenizer treats the whole text as one token.** The spaces stay
  inside the trigram stream (`E-Mail` → `e-mail`), which is what makes the
  compact column necessary in the first place.

## Decision

### 1. The C# side uses a measured table

`src/Nordmann.LUI/Normalization/tokenizer-fold.txt` holds the tokenizer's
behaviour for every code point of the Basic Multilingual Plane: **1,263
mappings and 25 removals**. It is generated by `tools/FoldTableGenerator`
and **verified against the live tokenizer by the parity test on every
build** — a table that no longer matches SQLite fails the build instead of
lying.

The C# side stays free of Unicode casing and normalisation: it neither
calls `ToLowerInvariant` nor `Normalize`, so it behaves the same under
`InvariantGlobalization=true` as under ICU. (Measured: under invariant
globalization `Normalize` is a **no-op** — `"é".Normalize(FormD)` keeps one
character instead of two. A rule that needs the decomposition cannot even
be *expressed* there.)

### 2. The transliteration runs before the folding

`Ä` → `Ae` → `ae`, not `Ä` → `a`. Both sides do it in this order, and the
SQL side applies the transliteration with `replace()` — which it can do,
because the folding happens in the tokenizer, not in the column.

### 3. The decomposed umlauts are transliterated too

A decomposed umlaut is a letter plus U+0308. macOS file names and some
clipboards deliver that form, and the two spellings would be two different
words — with one of them silently unfindable. The C# side transliterates
`a/o/u` followed by U+0308 and skips the mark; the SQL side replaces the
same six sequences.

### 4. The compact form drops an explicit list of separators

The specification says the compact form removes "everything except letters
and digits". SQLite cannot express that in a generated column, so both
sides work from the **same explicit list**: the ASCII punctuation, the
control characters that separate words, and the Unicode spaces, dashes,
quotes, the middle dot, the bullet and the guillemets.

**This is a deviation from ADR-0005's wording**, and it is deliberate: the two
sides have to agree *exactly*, or the C# compact form (which strips after
the folding) and the SQL compact column (which strips before it) would
differ, and a query would stop finding what it should.

### 5. The folding of the *application's* SQLite is verified at open time

The table is measured from the SQLite that `Microsoft.Data.Sqlite` 10.0.14
bundles. An application that loads a **different** SQLite folds text with
other tables — and an index that was stored with the old folding is now
invisible to the query.

⇒ **Decided for PR-003:** `LuiCatalog.Open` probes the folding of the
SQLite it is actually talking to (a few dozen code points — the table's
entries plus a few unlisted ones, a fraction of the full sweep) and
**fails with a clear error** when it differs from the table. The version
of the fold table is written to `lui_meta`, so an index stored with an
older table is detected and the application is told to `Rebuild()`.

## Consequences

- **The spec's ADR-0005 is superseded on two points**: the accent removal is not
  "Unicode decomposition" but SQLite's own table, and the compact form
  removes an explicit list rather than "everything except letters and
  digits". Both differences are recorded here and in
  `docs/normalization.md`.
- **The table is a maintenance obligation.** It has to be regenerated when
  SQLite changes its folding. The parity test turns that obligation into a
  build failure rather than a silent search failure.
- **The generator runs with ICU**, the library does not: the *report* about
  the two .NET rules needs the decomposition, the *table* comes from SQLite.
- **The parity test is the release gate**: it sweeps the whole Basic
  Multilingual Plane, and the release workflow runs all 685,829 words of the
  German word list against the live tokenizer.

## What was checked

| | |
|---|---|
| `The_fold_table_matches_the_tokenizer_for_every_code_point` | the table is the tokenizer's behaviour, over the whole BMP |
| `The_normalizer_and_the_tokenizer_agree_on_the_word_corpus` | the C# search form equals the tokenizer's view of the SQL column |
| `The_normalizer_and_the_tokenizer_agree_on_the_full_word_list` | the same for all 685,829 words — the release gate |
| `The_normalizer_and_the_tokenizer_agree_on_the_edge_cases` | the same for the characters a stride cannot reach for |
| `The_edge_cases_hold_the_measured_expectations` | the corpus file holds the measured expectations |
| `The_compact_form_of_the_sql_column_matches_the_compact_form_of_the_normalizer` | the SQL compact column and the C# compact form are the same text |
| `No_folded_character_is_a_separator` / `No_separator_is_folded_into_a_letter` | the folding and the separator set do not interfere |

## The scope of the claim

The table covers the **Basic Multilingual Plane**. SQLite also folds case
*outside* it (a lowercase query finds uppercase Deseret text), and the
C# side leaves those characters unchanged. It does not affect German or
emoji, and it cannot make the search fail: SQLite folds the query and the
indexed text alike, so both sides of the comparison still agree. The C#
side's view is simply the unfolded one for those characters.
